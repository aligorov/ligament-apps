ИНЦИДЕНТ «чёрный экран после назад» (2026-10-10, v1.1.21→1.1.23):
симптом — после «назад» из консоли контент окна macOS навсегда чёрный,
титлбар жив. v1.1.22 (порядок teardown: sync dispose → отложенный resize)
НЕ исправил — воспроизведено на живой сборке. Корневая причина (по
совокупности: оба порядка дают чёрное; пользователи свободно ресайзят окно
при живом стриме без чёрного; класс бага flutter-webrtc desktop): race
между unregister текстуры RTCVideoRenderer.dispose() и raster-потоком
Flutter — dispose впритык к pop-анимации/resize ловит raster на живом
кадре → дедлок композиции. Фикс v1.1.23: на macOS srcObject=null и
pc.close() остаются синхронными (стоп кадров), а нативный dispose текстуры
уезжает на +3с (raster гарантированно простаивает); resize окна на +500мс
безопасен при пустой текстуре.

Триггер: консоль не работает, если на ПК запущена только служба; попутно —
TCC-диалог записи экрана на Mac-вьюере и чёрный экран после завершения.

## 1. Требование

Подключение к «Консоли ПК» должно срабатывать в любом состоянии машины-хоста
(приложение закрыто, сеанс заблокирован, до входа в Windows). Приоритет —
Windows; macOS/Linux — после.

## 2. Инвентаризация (что реализовано; проверено кодом)

- Авто-восстановление сессии приложения из secure storage
  (`ligament-apps/lib/services/auth_state.dart:560-587`; 401 → logout — после
  logout/отзыва токена headless-логин НЕ восстановится). device_id
  персистентный (`:569-573`), argv парсится (`main.dart:63-65`).
- Owner-флоу стартует трансляцию без диалогов: `auth_state.dart:1528-1589`
  → `activateOwnerScreen` → `startScreenSharing` (`support_service.dart:630`).
- Прод-путь сессии — ТОЛЬКО атомарный в `handleGrant`
  (`2fa/internal/api/rdp_gateway.go:1161-1206`); `startOwnerScreenSession`
  (`:1540-1631`) в проде НЕ вызывается (только интеграционный тест) — его
  broadcast (`:1620-1623`) мёртв, живой broadcast один (`:1203-1205`).
- Службы Windows (обе LocalSystem): сторож с готовым `LaunchAppInSession`
  (`windows/service/service.cpp:128-160`); endpoint-агент с WSS по agent_key
  и диспетчером `HandleText` (`windows/endpoint_service/endpoint_service.cpp:843-874`).
  К консоли не подключены — проектное ограничение этапа 2.4
  (`docs/rdp-client-stage2-plan.md:545`).
- AgentHub сервера умеет слать агентам кадры (`rdp_agent_hub.go:377-423`).

## 3. Подтверждённые дефекты (аудит 2026-10-10)

- **Д1 (P1) Активация без объектной авторизации**: POST
  `/api/v1/app/support/{id}/activate-screen` (`rdp_gateway.go:1292-1340`)
  проверяет только «какой-то юзер + какое-то устройство»; в сторе
  (`support.go:1183-1288`) владелец сессии не сверяется с вызывающим; пустой/
  ненайденный `instance_id` пропускает гейт (`:1247`, `:1259`);
  `metadata.target_device_id` безусловно переписывается на вызывающего
  (`:1277-1281`); для `active` — ранний тихий успех (`:1214-1216`), настоящий
  хост не узнаёт о подмене. Окно — 60с `connecting`.
- **Д2** Broadcast owner-промпта при недоставке (`rdp_gateway.go:1203-1205`) —
  кадр уходит всем WS юзера, включая вьюера. SSE broadcast не получают.
- **Д3** Клиентский гейт `ownerScreenPromptTargetsThisDevice`
  (`auth_state.dart:60-80`): при `_registeredMachineId == null` проверка
  target_machine_id — no-op, провал до `return true`.
- **Д4** Роли сигналинга не разделены: гейт — membership без направления
  (`app.go:2772-2787`), релей доставляет любой сигнал (`:2763-2765`).
  Signaling-ручка ОТПРАВЛЯЕТ чужого юзера (`:2702-2705`) — именно эта ручка;
  отсутствие обходов в остальных путях не доказано (формулировка сужена).
- **Д5** Состояния ожидания: WS-open ставит `_isConnected=true`
  (`support_operator_screen.dart:335`) → guard гасит 25с-таймер (`:275`) →
  таймаута на «offer/P2P не пришёл» НЕТ ВООБЩЕ; таймер снимается в onTrack
  (`:513-517`) — это трек, не кадр; `onFirstFrameRendered` в плагине ЕСТЬ
  (`rtc_video_renderer_impl.dart:52,134`), приложением не используется.
- **Д6** Завершение: `session_ended` только верхний `data['type']` (`:672`)
  при SDP через нормализованный payload (`:632-636`); pop закрывает верхний
  route (диалог/чат), не консоль; lease-путь чистит без pop (`:160-176`);
  `_cleanupResources` не сбрасывает `_isConnected` (`:1237-1291`).
- **Д7** Рассинхрон `_ownDeviceId` — только узкий путь (пустой `device_id`
  в ответе логина при старых prefs, `auth_state.dart:965-969,569-573`);
  ротация сама по себе рассинхрона не даёт.
- **Д8** Регистрация машины: тихий отказ без ретрая (`auth_state.dart:1133-1135`)
  — источник `registeredMachineId == null` для Д3.
- **Д9** Службы к консоли не подключены (см. §2) — первопричина «только с
  запущенным приложением»; плитка «онлайн» врёт по endpoint-WSS.
- **Д10** Платформенные границы (интернет-верифицированы): захват из сессии 0
  невозможен; lock/logon/UAC = secure desktop, видит только SYSTEM-процесс в
  консольной сессии (паттерн RustDesk; «connect before login»);
  macOS: до-логин возможен через LaunchAgent в LoginWindow-сессии (RustDesk
  agent.plist), но ограничен TCC (нужна одноразовая GUI-выдача прав) и капризен;
  FileVault после перезагрузки: на Apple silicon/macOS 26+ том можно разблокировать
  по SSH при Remote Login — про трансляцию это ничего не говорит;
  Linux: X11 — захват свободный, Wayland — портал + PipeWire c restore_token
  (persist_mode 1/2, одноразовый, зависит от бэкенда) — «диалог всегда» неверно.

Связь Д2×Д3 с конкретным TCC-инцидентом на Mac — гипотеза до журналов
выполнения (см. §7).

## 4. Условия реализации (закреплены до кода)

1. **Авторизация активации — до любых изменений сессии**: проверка
   вызывающего, выбранной машины, устройства, экземпляра; отсутствующий/
   неизвестный экземпляр → отказ; уже активная сессия → успех только
   подтверждённому участнику.
2. **Атомарность проверок и перехода**: повторные и конкурентные запросы не
   меняют цель и не активируют завершённую сессию; одной проверки владельца
   в хендлере недостаточно.
3. **Первый кадр и управление — разные признаки готовности**:
   `onFirstFrameRendered` = изображение; управление = готовый DataChannel +
   разрешения; при переподключении готовность сбрасывается.
4. **Wake — промежуточный этап с ограниченным результатом**: запуск
   пользовательского приложения не решает доступ до входа в Windows и работу
   с secure desktop — это отдельный прототип (Ш6).

## 5. Порядок работ

- **Ш1. Активация (P1)** — закрыть Д1 по условиям §4.1–4.2. Объём: малый.
- **Ш2. Адресная доставка и роли** — убрать broadcast (Д2); initiator всегда
  заполнен; клиентский гейт fail-closed (Д3+Д8); роли offer/answer/ICE (Д4).
  Объём: малый.
- **Ш3. Состояния и таймауты** — цепочка
  `signal-ws → offer → ICE → track → first_frame → control-ready`, каждой
  стадии таймаут, понятная ошибка и повтор; `onFirstFrameRendered` как граница
  «изображение появилось»; сброс готовности при переподключении (Д5).
  Объём: средний.
- **Ш4. Завершение** — единый teardown: вложенные кадры, открытые диалоги,
  смерть хоста, потеря сети, сброс `_isConnected` (Д6). Объём: малый.
- **Ш5. Wake (v1)** — `agent_console_wake` в AgentHub → endpoint-служба →
  `LaunchAppInSession(--autoshare=<sid>)` → авто-логин → существующий
  owner-флоу; честные ошибки («нет вошедшего пользователя», «ПК офлайн»,
  «не удалось поднять»). Покрывает ТОЛЬКО «юзер вошёл, приложение закрыто».
  Объём: ~1–2 дня (сервер + C++ + Dart).
- **Ш6. Прототип до-входа/secure desktop (Windows VM)** — SYSTEM-процесс в
  нужной сессии + машинная авторизация; непрерывная проверка переходов
  `login → desktop → lock → unlock → UAC`, не один снимок. Только после
  успешного прототипа — оценка этапа. macOS/Linux — после Windows.
  Прототип может показать, что текущий захват/ввод экран входа/UAC не
  поддерживается и нужен отдельный нативный компонент — успешный Wake
  этого НЕ гарантирует.

## 6. Критерии приёмки

- чужой юзер / неверное устройство / отсутствующий экземпляр → отказ БЕЗ
  изменения БД;
- повторная и конкурентная активация → исходная цель сохранена;
- WS открыт, offer/видео нет → ограниченное ожидание, ошибка, повтор;
- изображение есть, канал управления закрыт → управление недоступно;
- завершение при открытом диалоге, потере хоста, переподключении → корректная
  очистка и понятный статус.

## 7. Диагностика

Структурированные события без контента кадров/SDP/секретов/ввода:
`{session_id, stage: prompt_sent | activated | offer | answer | ice | track |
first_frame | end, device_id, reason}` — сервер (audit_log при отправке
промпта и активации) и клиент (входы гейта + решение). Финальное
доказательство причины TCC-инцидента — только эти журналы выполнения.

## 8. Риски и поэтапный выпуск (обязательные гейты до выпуска)

Главный риск — починить запуск консоли, но сломать существующие SOS-сессии,
переподключение или доступ к нужному хосту. Поэтому внедрять по этапам, с
проверкой каждого.

| Изменение | Что может сломаться | Обязательная проверка |
|---|---|---|
| Строгая авторизация активации (Ш1) | Старые клиенты без `instance_id` перестанут подключаться | Совместимость версий; понятная ошибка и требование обновления |
| Удаление broadcast (Ш2) | Незарегистрированный хост перестанет получать запросы вообще | Точная привязка машины; повтор регистрации; честный статус доступности |
| Разделение ролей signaling (Ш2) | SOS, повторный offer и ICE restart могут блокироваться | Отдельные правила для Console и SOS; проверка переподключения |
| Новые тайм-ауты (Ш3) | Медленное подключение через relay будет ошибочно завершаться | Прямое соединение, relay, задержки, временная потеря сети |
| Единое завершение (Ш4) | Старый callback может закрыть уже восстановленное соединение | Привязка callbacks к конкретной попытке; повторная очистка безопасна |
| Wake приложения (Ш5) | Двойной запуск, неверная Windows-сессия, запрос входа вместо трансляции | Single-instance + IPC; несколько пользователей; отозванный токен |
| SYSTEM-процесс захвата (Ш6) | Чёрный экран или потеря ввода при lock, UAC, смене пользователя | Полный цикл переходов Windows, несколько мониторов, RDP-сеансы |
| Локальное истечение разрешения | Обрыв при кратком сбое Core либо продолжение после отзыва доступа | Продление срока, потеря Core, гарантированная остановка захвата/ввода |

**Блокирующие сценарии выпуска** (независимо от того, работает ли
изображение): подключение к другой машине и сохранение управления после
завершения доступа. Эти две проверки валят выпуск, даже если всё остальное
зелёное.

Ограничение последствий:

1. Ш1–Ш4 проверять на существующих Console и SOS ДО добавления Wake.
2. Ш5 проверять отдельно на Windows с вошедшим пользователем.
3. Ш6 сначала на VM, затем на ограниченной группе машин.
4. Отключение новой Console — политикой в БД, не задевая существующий RDP.
5. Проверить обновление и откат службы вместе с совместимостью серверной
   версии (старый клиент ↔ новый сервер и наоборот).

Обещать отсутствие поломок нельзя; риски выше превращены в обязательные
проверки до выпуска.
