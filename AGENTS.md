# Правила сборки и разработки Ligament Apps

## 1. Сборка клиентских приложений (Строгое правило)
- **Все релизные дистрибутивы приложений (Windows MSI, macOS, Linux, Android, iOS)** собираются **СТРОГО В GITHUB ACTIONS**:
  - Workflow: `.github/workflows/build_clients.yml`.
  - Триггер: отправка тега версии `v*` (например, `v1.1.15`).
  - Процесс релиза:
    1. Обновить номер версии в `pubspec.yaml` (например, `version: 1.1.15+41`).
    2. Закоммитить изменения: `git commit -am "..."`.
    3. Создать аннотированный тег: `git tag -a v1.1.15 -m "release v1.1.15: ..."`.
    4. Отправить тег на remote: `git push origin main v1.1.15`.
- Локально на девелоперской машине запускаются только тесты (`flutter test`), анализ (`flutter analyze`) или локальная отладка (`flutter run`).

## 3. Git-гигиена: ветки, коммиты и PR
- **Имена веток**: короткие, максимум из трёх слов через дефис, без префиксов `feat/` или слэшей.
  - Примеры: `qr-scanner-fix`, `biometric-flow`, `tray-icon-linux`.
- **Сообщения коммитов и PR**: формат Conventional Commits `type(scope): summary`.
  - Типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `perf`.
  - Область (scope): `ui`, `api`, `auth`, `screens`, `models`, `i18n`, `windows`, `macos`, `android`, `ios`.
  - Примеры: `fix(auth): handle expired refresh token gracefully`, `feat(ui): add compact mode for desktop tray`.
- **UI-изменения в PR**: для любых заметных правок экранов или компонентов прикладывать скриншот или короткое описание визуального поведения в теле PR.

## 4. Архитектура и стиль Dart / Flutter (Anti-Bloat & Pragmatism)
- **Локальность и запрет преждевременных абстракций**:
  - Не создавать кастомные виджеты-обертки над стандартными компонентами Flutter, если они используются только один раз на одном экране. Инлайнить виджеты по месту вызова.
  - Извлекать виджет в отдельный класс только при реальном переиспользовании или когда размер метода `build` препятствует читаемости и точечной перерисовке.
- **Семантические токены тем (Theme Tokens)**:
  - Запрещено хардкодить статические цвета (`Colors.blue`, `Color(0xFF...)`) в бизнес-виджетах.
  - Использовать `Theme.of(context).colorScheme` и семантические роли (`colorScheme.error`, `colorScheme.primary`, `surface`, etc.).
  - Сохранять поддержку как светлой, так и темной темы во всех новых экранах.
- **Валидация на границах (Boundary Validation)**:
  - Парсинг и валидация входящих данных из API/сокетов/хранилища производятся строго в `models` / `api` слое при десериализации (JSON).
  - В UI передаются строго типизированные модели данных, экраны не должны выполнять защитную валидацию типов на лету.
- **Отказ от спекулятивной сложности**:
  - Не усложнять стейт-менеджмент многослойными конструкциями, если достаточно простого и предсказуемого потока данных.
  - Не добавлять обходные пути под редкие невоспроизводимые кейсы без подтверждения и обсуждения.
- **Чистота и производительность Dart**:
  - Всегда использовать `const` конструкторы для виджетов, где параметры неизменны (снижает нагрузку на сборщик мусора и предотвращает лишние ребиbuild).
  - Предпочитать `StatelessWidget` там, где состояние управляется внешним сервисом/провайдером.
  - Избегать глубоких вложенностей `if / else`, использовать ранние возвраты (early returns / guard clauses).
  - Избегать `dynamic` и приведения типов `as Type` без предварительной строгой проверки.

## 5. Тестирование и проверки (Checks)
- Перед созданием коммита и тега убедиться в чистоте статического анализатора и тестов:
  ```bash
  flutter analyze
  flutter test
  ```
- `flutter analyze` должен возвращать **0 ошибок и 0 предупреждений** (clean analyzer).
- Тестировать реальные пользовательские сценарии (`testWidgets`), избегать избыточного мокирования базовых механизмов Flutter.
